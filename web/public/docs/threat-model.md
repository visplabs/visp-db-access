# Threat model

This document says who can attack a deployment of visp-gate, what the
gateway does about each attack, and what is left over. It is written for a
security reviewer who has to decide whether an AI agent may reach a
production database through the gateway.

It is made from the code and from the [security model](security-model.md),
which describes the mechanisms in more detail. Each mitigation names the file
or the test that shows it. Tests are in `crates/*/tests/`; a name such as
`hardening.rs: the_database_is_the_judge_for_agents` is a test function in
`crates/vda-server/tests/hardening.rs`.

To report a problem, see [How to report a problem](#how-to-report-a-problem).

## What is protected

| Asset                                                          | What can go wrong                                                              |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Rows in the target databases                                   | Read by someone who should not, changed, deleted, or locked                    |
| Protected columns, blocked tables                              | Their values reach an agent, and through it a model provider or an attacker    |
| The target database itself                                     | Slowed down or stopped by heavy queries, locks or too many connections         |
| Database logins                                                | The password that the gateway holds for a target database is disclosed         |
| Agent tokens and people's logins                               | Someone else acts as an agent or as a person                                   |
| The record                                                     | Query history, the audit log and write receipts are changed, removed or forged |
| The cloud identity for discovery and the notice signing secret | Disclosed, they let someone list your cloud databases or forge a notice        |
| The master key                                                 | It decrypts stored logins, signs receipts and seals the audit log              |

## Who the actors are

| Actor                      | What they have                                                                                        | What they want                                 |
| -------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| A careless agent           | A valid agent token. It means well and makes mistakes.                                                | To finish its task                             |
| A prompt-injected agent    | A valid agent token, and instructions from an attacker that it read in a ticket, a web page or a row. | Whatever the attacker's text asks for          |
| A malicious agent operator | An account in the gateway, and the agents and tokens they own.                                        | More than their own access; no trace           |
| A member without access    | An account in the gateway with no grant on the database.                                              | To read or change that database                |
| A metadata-database admin  | Full access to the PostgreSQL metadata store. Not the master key.                                     | Access to targets; to rewrite the record       |
| A network attacker         | A place on a network between the parts, or on the internet. No account.                               | Tokens, sessions, data; a way to reach targets |
| A compromised gateway node | Code running as the gateway process on one node.                                                      | Everything                                     |

The first two are the reason the gateway has an agent door. An agent is
treated as untrusted from the first call: the gateway assumes that any agent
can become a prompt-injected agent at any moment.

## Trust boundaries

```text
   agent (model + tools)              person (browser)
        │ bearer token                      │ session cookie + CSRF header
        ▼  B1                               ▼  B2
 ┌──────────────────────────── gateway node ───────────────────────────┐
 │  network gate → identity → SQL guard → limits → execution → masking │
 │  holds in memory: master key, database logins, rows on their way    │
 └───────┬───────────────────────────┬──────────────────────┬──────────┘
         │ B3  cluster login,        │ B4  SQL              │ B5  HTTPS
         │     or agent login        │                      │     (off by default)
         ▼                           ▼                      ▼
   target databases            metadata store        notice receiver
```

| Boundary | Between                      | What crosses it                                                                                    |
| -------- | ---------------------------- | -------------------------------------------------------------------------------------------------- |
| B1       | An agent and the gateway     | Tool calls with SQL and a task; masked rows, refusals with a fix                                   |
| B2       | A person and the gateway     | The console and its API: queries, policies, grants, approvals                                      |
| B3       | The gateway and a target     | Guarded SQL under the cluster's login, or under the agent login for agents                         |
| B4       | The gateway and its metadata | Users, grants, policies, encrypted logins, approvals, history, audit, agent steps                  |
| B5       | The gateway and a webhook    | A notice that a request waits: names and states, never SQL or rows. The reason only when turned on |

Everything inside the gateway node is trusted. The target database is trusted
to enforce its own grants. The metadata store is trusted for everything
except the secrecy of stored logins and the integrity of sealed audit rows
and receipts. Agents, browsers, networks and the notice receiver are not
trusted.

## Threats and what the gate does

Each table has the same columns: the scenario, what the gate does, where to
see it, and what remains.

### A careless agent

| #   | Scenario                                                                                  | What the gate does                                                                                                                                                                                                                      | Evidence                                                                                                                                                                                                                                               | What remains                                                                                                                                                                |
| --- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | It reads a whole large table.                                                             | The guard adds `LIMIT max_rows + 1` to the statement. Execution stops at the row cap and at 32 MiB, under a statement timeout, in a read-only transaction that is rolled back. One answer holds at most 1,000 rows and about 1 MB.      | `crates/vda-guard/src/rewrite.rs`; `safety.rs: limit_rewrites_and_original_flags`; `guarded.rs: postgres_truncation`, `postgres_statement_timeout`; `scripts/demo-agent.sh` step 6                                                                     | A statement inside the limits can still be heavy. The cost gate (`max_cost`) is off until someone sets it. Timeouts and the concurrency limit are per cluster and per node. |
| C2  | It sends `DELETE FROM orders`, or an `UPDATE` with no `WHERE`.                            | A write with no `WHERE`, or with one that the guard can tell is always true (`1=1`, `x=x`, `id=1 OR true`), is denied. Every other write by an agent needs a person's approval, whatever the policy lets people do.                     | `crates/vda-core/src/query.rs` ("An agent never writes on its own word"); `safety.rs: write_predicates`, `constant_predicate_folding_cannot_allow_unrestricted_writes`; `hardening.rs: agent_queries_are_capped_recorded_and_never_write_on_their_own` | A `WHERE` that is too wide, or always true in a way the guard does not see (`id > 0`), passes the guard. | C3  | It hides a write in a read: `WITH x AS (DELETE …) SELECT …`, or `EXPLAIN ANALYZE UPDATE`. | The guard walks the whole statement and classes it as a write. SQL that it cannot parse or does not support is denied.                                                                                                                  | `safety.rs: whole_ast_writes_and_explain`, `lexical_and_complexity_bypasses_fail_closed`; `attack_corpus.rs: attack_corpus`; the fuzz target in `crates/vda-guard/fuzz/`                                                                               | A function defined in the database can write when it is called from a `SELECT`. | C4  | It is refused and tries again, in a loop.                                                 | Every refusal carries a `fix`: one action word and a hint. | C5  | It reads personal data it did not need.                                                   | Protected columns come back as `••••••`. The gate does not find personal data by itself.                                                                        |
| C6  | It asks for a write that looks right and is not.                                          | Nothing of it runs. At execution the write runs only on the rows that the dry run locked; if they changed, it fails with `effect_changed`. | `crates/vda-server/src/approvals.rs`; `hardening.rs: an_agent_proposes_a_write_sees_no_rows_and_a_person_decides`, `a_write_is_previewed_bound_to_its_effect_and_leaves_a_signed_receipt`                                                              | The approver can be wrong. MySQL has no dry run and binds nothing. A dry run advances sequences and fires triggers.                                                         |

### A prompt-injected agent

Assume that the agent does whatever an attacker's text tells it, with all the
skill of the model, inside what its token allows.

| #   | Scenario                                                                                              | What the gate does                                                                                                                                                                                                                                                                                                                                                        | Evidence                                                                                                                                                                                                                                                                            | What remains                                                                                                                                                                                                                                                                                                          |
| --- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I1  | It sends everything it can read to the attacker.                                                      | It can read only the databases its owner put in its list, at most at its level, never more than its owner can at that moment. Protected columns are masked and blocked tables are closed. The row cap and the hourly budget bound how fast it reads.                                                                                                                      | `crates/vda-core/src/access.rs` (`narrow`); `hardening.rs: agents_are_owned_scoped_and_managed_only_by_the_right_people`, `agent_queries_are_capped_recorded_and_never_write_on_their_own`                                                                                          | **Data that is allowed and not masked leaves with the agent.** The gate does not see where an agent sends what it read. With the defaults for a production database that is up to 1,000 rows a query and 300 queries an hour. Give agents narrow lists, block what they do not need, and lower the budget.            |
| I2  | It gets a protected value out under another name: an alias, an expression, JSON, a whole row.         | A statement that renames a protected column, wraps it in an expression, or serializes a row of a table with protected columns is denied (`masked_data_transformation`, `masked_data_serialization`). Database error text is hidden for such tables.                                                                                                                       | `security.rs: masked_columns_cannot_be_renamed_or_derived_to_escape_masking`, `masked_serialization_is_denied_but_wildcard_columns_survive`, `masked_columns_cannot_escape_through_dml_returning`; `hardening.rs: query_intent_is_durable_unique_fail_closed_and_masks_diagnostics` | The rule reads SQL text and column names. A view, a function defined in the database, or a copy of the column under another name is not covered. On PostgreSQL the agent login closes views and functions (I4). A copy of a protected value in a column with another name stays readable unless you mark or block it. |
| I3  | It learns a protected value without selecting it: `WHERE email LIKE 'a%'`, `ORDER BY email`, a count. | Nothing, with the gateway alone: a filter, a sort or a join on a protected column is allowed, and the answer tells something about the value. With an agent login the database refuses any use of a column that is not granted.                                                                                                                                           | `security.rs: masked_columns_cannot_be_renamed_or_derived_to_escape_masking` (the list of statements that pass); `hardening.rs: the_database_is_the_judge_for_agents`                                                                                                               | **Masking hides values in results. It is not secrecy against an agent that asks many questions.** For that, use the agent login, or block the table. Aggregates over allowed columns can also reveal single rows.                                                                                                     |
| I4  | It reads a blocked table through a view, a partition or a function that the guard cannot see through. | With the gateway alone the block is a rule on names, and a view over a blocked table leaks. With an agent login the database decides: it holds column grants for exactly what the policy allows, and no grant on any view. If the login can do more than the policy, agents are refused (`database_setup_drift`).                                                         | `crates/vda-core/src/judge.rs`; `hardening.rs: the_database_is_the_judge_for_agents` ("The guard does not know that the view reads the blocked table: it leaks.")                                                                                                                   | PostgreSQL only. A database administrator must run the script. Table and column names, comments and view sources stay visible in the catalog. A new object open to `PUBLIC` can be readable for up to five minutes.                                                                                                   |
| I5  | It calls a dangerous function or reads a system catalog.                                              | Sleeps, file access, large objects, `dblink`, advisory locks and catalogs with credentials are denied in every position of a statement.                                                                                                                                                                                                                                   | `crates/vda-guard/src/functions.rs`, `tables.rs`; `safety.rs: functions_in_every_position`, `locking_and_file_writes`                                                                                                                                                               | The list is a deny list. A function defined in the database is not inspected. Database privileges remain the primary control.                                                                                                                                                                                         |
| I6  | It asks for a harmful write with a reason that sounds right.                                          | The agent's reason is one line of plain text. The approver also sees the SQL and that an agent asked, and on PostgreSQL the rows before and after from the dry run. The owner of the agent cannot approve. On PostgreSQL an agent's write must be previewed before it can be approved, and a statement that calls a function defined in the database cannot be previewed. | `hardening.rs: an_agent_proposes_a_write_sees_no_rows_and_a_person_decides`, `the_attacks_found_on_safe_writes_stay_closed`                                                                                                                                                         | **A person who approves without reading.** The gate makes the effect visible; it cannot make anyone look. Triggers, defaults and row-security policies on the table run in the dry run and in the write, and are not checked. On MySQL there is no preview and no function check: the approver has only the SQL.      |
| I7  | It uses the write request to learn data: the dry run's count, or an error.                            | The agent never sees rows, and no count before the write has run. A failed write gives one of three fixed sentences. On PostgreSQL, before it is stored, the request is checked as the agent's own read, in a read-only transaction.                                                                                                                                      | `crates/vda-server/src/approvals.rs` (`status_for_agent`, `failure`); `hardening.rs: an_agent_that_follows_the_write_fix_is_not_stopped_and_reads_a_coded_outcome`                                                                                                                  | After an approved write runs, the agent learns how many rows changed.                                                                                                                                                                                                                                                 |
| I8  | It floods the gateway, the database or the approvers.                                                 | 120 calls a minute, the hourly budget, the per-cluster concurrency limit and the statement timeout. One proposal at a time, ten open requests and 30 an hour; five refused proposals stop `propose_write` for ten minutes.                                                                                                                                                | `crates/vda-server/src/mcp.rs`; `hardening.rs: agent_tools_read_guarded_data_teach_on_refusal_and_stop_loops`, `an_agent_proposes_a_write_sees_no_rows_and_a_person_decides`                                                                                                        | Per-node counters allow each limit once per node. Ten open requests still cost a person's time. The limits are per agent, and one person can own up to 50 agents.                                                                                                                                                     |
| I9  | It keeps going after someone noticed.                                                                 | Pausing or deleting the agent, revoking its token or disabling its owner refuses the next call with 401 and cancels the queries it is running on that node. Rows held for `fetch_rows` are dropped. A paused agent's approved write does not run.                                                                                                                         | `hardening.rs: an_agent_token_works_only_at_the_agent_door_and_only_while_everything_is_valid`; `agent_session.rs: held_rows_end_with_a_pause_a_revoke_a_change_and_the_memory_caps`                                                                                                | On other nodes a running query ends at its statement timeout. A pause by an administrator can be undone by the owner; delete the agent or disable the owner for a stop that holds.                                                                                                                                    |
| I10 | It reads text in a row that carries the next injection.                                               | Nothing. Rows are data from your database and are returned as they are.                                                                                                                                                                                                                                                                                                   |                                                                                                                                                                                                                                                                                     | Treat what an agent reads from a database as untrusted input to the agent.                                                                                                                                                                                                                                            |

### A malicious agent operator

A person with an account who owns agents and holds their tokens.

| #   | Scenario                                                                  | What the gate does                                                                                                                                                                                                                                        | Evidence                                                                                                                                                                   | What remains                                                                                                                                                                       |
| --- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| O1  | They use an agent to reach more than they can reach themselves.           | An agent's access is its owner's access at the time of the request, narrowed to the agent's list and level. It has no organization powers, even when its owner is an organization administrator. When the owner loses a grant, the agent loses it.        | `crates/vda-core/src/access.rs`; `hardening.rs: agents_are_owned_scoped_and_managed_only_by_the_right_people`, `a_token_cannot_be_minted_while_its_owner_is_losing_access` | None known.                                                                                                                                                                        |
| O2  | They use an agent to write without a second person.                       | The owner is the requester of the agent's write, and a requester cannot approve their own request. Both people's access is checked again when the write runs.                                                                                             | `integration.rs: authenticated_crud_policy_authorization_and_four_eyes`; `hardening.rs: an_agent_proposes_a_write_sees_no_rows_and_a_person_decides`                       | Two people who agree to misuse the gate. A person with two accounts: that is for your identity management to prevent.                                                              |
| O3  | They use the agent token on the API for people, or a session on the door. | The session API never accepts an agent token, and the agent door never accepts a session.                                                                                                                                                                 | `hardening.rs: an_agent_token_works_only_at_the_agent_door_and_only_while_everything_is_valid`                                                                             | None known.                                                                                                                                                                        |
| O4  | They let the agent act and deny it afterwards.                            | Every query is in history under the owner with the agent's id and its task, written before the query runs. Every tool call that passes the call-rate and argument checks is an `agent.tool` audit event. The audit log is sealed into a keyed hash chain. | `hardening.rs: query_intent_is_durable_unique_fail_closed_and_masks_diagnostics`, `agent_door_speaks_the_protocol_and_refuses_everything_else`; `audit_chain.rs`           | `agent.tool` events go through a bounded queue and can be lost in a crash or under overload; query history cannot. The record of steps is a convenience and is not tamper-evident. |
| O5  | A token leaks from the machine where the agent runs.                      | Only the token's SHA-256 digest is stored. A token lives at most 90 days, can be revoked, and works only from addresses in the network allowlists. Disabling the owner, a password change and a role change revoke every token of their agents.           | `crates/vda-core/src/agents.rs`; `hardening.rs: an_agent_token_works_only_at_the_agent_door_and_only_while_everything_is_valid`                                            | **Whoever holds a valid token is the agent** until someone revokes it. The allowlists are empty by default. Keep tokens out of prompts and logs.                                   |

### A member without access

| #   | Scenario                                                             | What the gate does                                                                                                                                                                          | Evidence                                                                                                                                                                                                                                      | What remains                                                                                        |
| --- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| M1  | They query a database they have no grant on.                         | Access is the highest unexpired grant on the cluster or its project; with none the answer is 403. Lists show only what the caller can reach.                                                | `security.rs: rbac_uses_maximum_unexpired_grant`, `rbac_resolves_maximum_level_and_expiry_boundary`; `integration.rs: authenticated_crud_policy_authorization_and_four_eyes`                                                                  | None known.                                                                                         |
| M2  | They give themselves access, or keep it past its end.                | Only an administrator of the scope can grant. A scoped administrator cannot grant to themselves or beyond the end of their own authority. Changing a cluster's endpoint needs its password. | `hardening.rs: endpoint_changes_and_delegation_cannot_reuse_or_extend_authority`, `grant_directory_is_paginated_filtered_and_scoped_to_administered_scopes`                                                                                   | An organization administrator can do everything in the gateway. Keep that role small.               |
| M3  | They read other people's queries, agents or the audit log.           | Members see their own history. An agent, its sessions and its steps are "not found" for everyone but its owner and organization administrators. | M4  | They guess a password.                                               | Passwords are hashed with Argon2id. Put the console behind your own access layer.  |
| M5  | They make a person's browser act: a forged request or a framed page. | State-changing requests need a custom header that a foreign page cannot send. The session cookie is `HttpOnly`. Responses carry a content security policy that forbids framing.             | `http.rs: csrf_rejects_missing_and_wrong_headers_with_contract_error`; `crates/vda-server/src/app.rs` (response headers)                                                                                                                      | A script injected into the console itself would act as the person. The policy allows inline styles. |

### A metadata-database admin

Someone who can read and write the PostgreSQL metadata store and does not
have the master key.

| #   | Scenario                                                 | What the gate does                                                                                                                                                                                                                                                                           | Evidence                                                                                                                                                                                                                                            | What remains                                                                                                                                                                                                                                                                                             |
| --- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | They read the stored database logins.                    | Passwords are encrypted with AES-256-GCM under the master key and bound to their cluster's id. A password moved to another cluster's row does not decrypt.                                                                                                                                   | `crates/vda-core/src/crypto.rs`; `security.rs: secrets_are_bound_to_cluster_and_detect_tampering`, `encryption_uses_fresh_nonces_and_rejects_bad_keys`                                                                                              | The password is bound to the cluster's id, not to its host. See D4.                                                                                                                                                                                                                                      |
| D2  | They use a stored token or session.                      | Agent tokens and session tokens are stored as SHA-256 digests, user passwords as Argon2id hashes.                                                                                                                                                                                            | `crates/vda-core/src/agents.rs`; `crates/vda-server/src/auth/mod.rs`                                                                                                                                                                                | They can insert a session or a token of their own. See D4.                                                                                                                                                                                                                                               |
| D3  | They change, delete or add audit rows to hide something. | Every audit row is sealed into an HMAC chain with a key derived from the master key. A changed, deleted, inserted or reordered sealed row shows, in the background check, in the console and in the offline command. Write receipts are signed with another key derived from the master key. | `crates/vda-core/src/chain.rs`; `audit_chain.rs: each_kind_of_tampering_is_found_with_its_kind_and_position`, `relabelling_a_link_as_another_keys_does_not_hide_a_changed_row`, `the_offline_check_reads_only_and_its_exit_code_says_what_it_found` | A row that is not sealed yet (a few seconds). The end of the chain, unless checkpoints are kept outside the database. A false row written the normal way. Query history and agent steps are not in the chain. See [the limits](security-model.md#a-tamper-evident-audit-log).                            |
| D4  | They give themselves access by editing rows.             | Nothing. Grants, policies, users, sessions, agents and approvals are plain rows. The gateway believes its metadata.                                                                                                                                                                          |                                                                                                                                                                                                                                                     | **A metadata-database admin can act as anyone in the gateway**, loosen a policy, or mark a request as approved. They can also change the host of a cluster, and the gateway then offers that cluster's login to another server. The audit chain shows a changed audit row; it does not stop any of this. |

Treat write access to the metadata store as administrator access to every
target behind the gateway. Give the metadata database its own instance and
its own small set of administrators.

### A network attacker

| #   | Scenario                                               | What the gate does                                                                                                                                                                                                                                                                                        | Evidence                                                                                                                                                                  | What remains                                                                                                                                   |
| --- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| N1  | They listen between a client and the gateway.          | The gateway serves plain HTTP and expects TLS in front of it. With `VISP_GATE_COOKIE_SECURE` (on by default) the session cookie is `Secure` and responses carry HSTS.                                                                                                                                     | `crates/vda-server/src/app.rs` (response headers); [Deployment](deployment.md)                                                                                            | **Without TLS at the ingress, agent tokens and sessions cross the network in clear text.** The gateway does not check this for you.            |
| N2  | They listen between the gateway and a target.          | Each cluster has a TLS mode; `verify_full` checks the certificate and the host name.                                                                                                                                                                                                                      | `crates/vda-connectors/src/tls.rs`                                                                                                                                        | A cluster can be set to `disable`. A DNS change between the address check and the connection is a rebinding risk; use outbound firewall rules. |
| N3  | They reach the gateway from a network that should not. | An organization allowlist and a per-cluster allowlist, for people and for agents. | N4  | They make a person's browser call the agent door.      | The door takes a bearer token only, never a cookie, and refuses any request with an `Origin` header.                                                                                                                                                                                                      | `crates/vda-server/src/mcp.rs`; `hardening.rs: agent_door_speaks_the_protocol_and_refuses_everything_else`                                                                | None known.                                                                                                                                    |
| N5  | They use the gateway to reach an internal address.     | Target addresses are checked when a pool is made and at every health check: metadata, link-local and zero-network addresses are always refused, in every IPv6 form, and loopback unless `VISP_GATE_ALLOW_PRIVATE_TARGETS` is on. A notice goes only to a public address that the gateway resolved itself. | `crates/vda-core/src/network.rs`; `security.rs: dangerous_target_addresses_are_refused`; `notice_sender.rs: without_local_development_nothing_on_this_machine_is_reached` | Private (RFC 1918) database targets are allowed, because that is where databases are. Only an administrator can add a target.                  |
| N6  | They read `/metrics`.                                  | The network gate applies, and a bearer token when `VISP_GATE_METRICS_TOKEN` is set, compared in constant time.                                                                                                                                                                                            | `hardening.rs: approval_lists_recovery_cidrs_and_metrics_are_enforced`                                                                                                    | Without the token, anyone the network gate lets in can read the metrics.                                                                       |

### A compromised gateway node

| #   | Scenario                                  | What the gate does                                                                                                                                                                                                       | Evidence                                                                                    | What remains                                                                                                                                                                                                                                                                                                                  |
| --- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1  | Someone runs code as the gateway process. | Nothing protects against this. The process holds the master key, the metadata login and, in memory, the logins of the targets it has used.                                                                               |                                                                                             | **Everything the gateway can do, the attacker can do**: read and write every target with the cluster logins, forge receipts and audit links, read rows that are passing through or held for `fetch_rows`. The node also holds the cloud identity it uses for discovery and, decrypted for sending, the notice signing secret. |

## What this does not protect against

Read this list before you rely on the gate.

- **An agent that has database credentials of its own.** The gate guards what
  comes through it. An agent with a connection string in its environment goes
  around it. Take the credentials away and close the network path.
- **A compromised master key.** With the key someone can decrypt every stored
  login, sign receipts and make an audit chain that verifies for any content.
- **A malicious administrator of the metadata database.** They can act as
  anyone in the gateway (D4). The hash chain shows changes to sealed audit
  rows and nothing else.
- **A compromised gateway node.** See G1.
- **Data that is allowed and not masked.** An agent may read it, and may send
  it anywhere. The gate does not classify data and does not watch what an
  agent does with an answer.
- **Inference.** Filters and sorts on protected columns, and aggregates over
  allowed ones, reveal facts about values that are never returned (I3).
- **Views and functions, when the gateway alone enforces the policy.** The
  guard reads SQL text. It does not resolve search paths or look inside a
  view or a function defined in the database. The agent login covers this on
  PostgreSQL only.
- **A reviewer who approves without reading.** The preview shows what a write
  changes. The decision is a person's.
- **Side effects of a dry run.** It advances sequences and fires triggers,
  and what a trigger does outside the transaction is not rolled back.
- **MySQL writes.** No dry run and no binding. Rollback needs InnoDB, DDL
  commits by itself, and the server-side time limit covers `SELECT` only.
- **The end of the audit chain and rows not sealed yet.** A chain cut at its
  end verifies as a shorter chain, unless a checkpoint is kept outside the
  database. A row can be changed in the seconds before it is sealed.
- **Agent steps.** The record of steps can lose steps under load and can be
  changed by someone with the metadata database. Use the audit log and query
  history to prove what happened.
- **Held rows.** Rows held for `fetch_rows` stay in a node's memory until five
  minutes after the last page, and up to 30 seconds more until a sweep frees
  them. A memory dump shows them. Set
  `VISP_GATE_HELD_RESULTS_MAX_BYTES=0` to hold nothing.
- **Limits that are counted per node.** Concurrency, the call rate, the stop
  after five refusals and login throttling are kept on each node.
- **Availability of the gateway.** There is no protection against a flood
  from the network beyond the limits above. Put it behind your own ingress.

## Assumptions

The claims above hold when these are true:

1. The only network path from agents to the target databases is the gateway,
   and agents hold no database credentials.
2. TLS ends in front of the gateway, and `VISP_GATE_COOKIE_SECURE` is on.
3. The master key is in a secret store, apart from the metadata database, and
   the people who administer one do not administer the other.
4. Each cluster login has the fewest database rights that fit its use. The
   gateway is defense in depth on top of database privileges, not in place of
   them.
5. The metadata database is PostgreSQL 14 or newer, on an instance with few
   administrators.
6. Policies are set by people who know the data: the gateway masks and blocks
   what it is told to.
7. Approvers read the SQL and the preview before they approve.
8. Audit checkpoints (`audit_checkpoint` log lines) are kept in a log store
   that the metadata database's administrators cannot change.
9. Organization administrators are few. They can change every policy and
   grant.

## How to report a problem

Report a vulnerability privately, as SECURITY.md describes.
A way around the SQL guard, the approvals, the masking or the agent door is
in scope. So is a claim in this document that the code does not keep: say
which row, and what you saw.
